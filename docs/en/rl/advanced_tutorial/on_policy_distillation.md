# On-Policy Distillation

This guide describes the On-Policy Distillation (OPD) capabilities currently supported by XTuner, including the available distillation targets, how to combine OPD with policy gradient (PG), how to configure training-objective weights and multi-Teacher routing, and how to choose between a Rollout Teacher and a Training-side Teacher.

OPD uses sequences generated by the current Student policy as training data. A Teacher then provides token-level targets for those sequences:

```text
Student rollout
  -> Teacher computes sampled-token or Top-K targets
  -> Align targets with training labels
  -> PG-OPD or direct distillation
  -> Update Student
```

In this guide, MOPD means Multi-Teacher OPD: data from different sources can be routed to different Teachers. It does not necessarily mean that task reward is mixed into the objective; whether task reward is used is controlled by `task_adv_weight`.

## Quick Selection

First choose the distillation target, then choose where the Teacher runs. These two dimensions can be combined independently.

### Distillation Targets

| Target | `loss_mode` | `use_policy_gradient` | `top_k` | Optimization |
| --- | --- | ---: | ---: | --- |
| sampled-token | `k1` | `True` | Unset | Add the distillation signal to the advantage, then compute the PG loss |
| Teacher Top-K | `forward` | `False` | Required | Direct backpropagation through Top-K forward KL with tail mass |
| Teacher Top-K | `reverse` | `False` | Required | Direct backpropagation through Top-K reverse KL with tail mass |
| Teacher Top-K | `forward_kl_topk` | `False` | Required | Direct backpropagation through truncated forward KL over the Teacher Top-K |

Sampled-token currently supports only `k1 + PG`. `k1` cannot use direct backpropagation, and the three Top-K modes cannot use PG.

### Teacher Runtime

| Teacher runtime | sampled-token | Top-K | How the Teacher runs |
| --- | ---: | ---: | --- |
| Rollout Teacher + LMDeploy | Supported | Supported | Independent HTTP service |
| Training-side Teacher | Supported | Supported | Frozen model inside each Training Worker |

With a Rollout Teacher, XTuner can launch the Teacher service together with Student training, or connect to endpoints that are already running. A Training-side Teacher does not require an endpoint; the training engine loads the Teacher checkpoint directly.

```{note}
All Teachers in one `DistillationConfig` must use the same runtime type. They must all be `RolloutTeacherConfig` instances or all be `TrainTeacherConfig` instances; the two types cannot be mixed.
```

## Core Configuration

OPD has three configuration layers:

- `DistillationLossConfig` defines the distillation target, PG loss, and objective weights.
- `RolloutTeacherConfig` or `TrainTeacherConfig` defines where the Teacher runs.
- `DistillationConfig` combines the loss, Teacher list, and data-source routing.

The same `DistillationLossConfig` must be passed to both the Training Worker and `DistillationConfig`:

```python
from xtuner.v1.rl.distillation import DistillationConfig
from xtuner.v1.rl.loss import DistillationLossConfig
from xtuner.v1.rl.trainer import WorkerConfig

loss_cfg = DistillationLossConfig(...)

train_worker_cfg = WorkerConfig(
    ...,
    loss_cfg=loss_cfg,
)

distillation_config = DistillationConfig(
    loss_config=loss_cfg,
    teachers=[...],
    data_source_teacher_map={...},
)
```

The Trainer checks that `train_worker_cfg.loss_cfg == distillation_config.loss_config`. Finally, pass `distillation_config` to `RLColocateTrainerConfig` or the corresponding RL Trainer configuration:

```python
trainer = RLColocateTrainerConfig(
    ...,
    train_worker_cfg=train_worker_cfg,
    distillation_config=distillation_config,
)
```

Common RL loss settings such as `policy_loss_cfg`, `use_kl_loss`, rollout importance sampling, `mode`, and `chunk_size` remain available. See [Loss](loss.md) for the shared fields. In particular:

- `loss_mode` selects the OPD target.
- `use_kl_loss`, `kl_loss_coef`, and `kl_loss_type` control the standard KL penalty against a Reference Model.
- The OPD Teacher and Reference Model have different roles. Enabling OPD does not require enabling Reference KL.

## Sampled-Token PG-OPD

Sampled-token OPD does not ask the Teacher to select new tokens. The Student first generates tokens, and the Teacher computes log probabilities only for those same tokens.

```text
Student rollout
  -> Student sampled tokens
  -> Teacher computes log probabilities for the same tokens
  -> Align with shifted labels
  -> Build the k1 distillation signal
  -> Combine with task advantage
  -> Policy gradient loss
```

The training-target contract is:

```text
teacher_logprobs: [B, T]
target_token_ids: None
```

Let the old Student log probability at each valid token be $\ell_{old}$ and the Teacher log probability be $\ell_T$. The `k1` distillation signal is:

$$
d_{OPD} = \ell_{old} - \ell_T
$$

XTuner detaches this signal and combines it with the task advantage:

$$
A_{combined}
= w_{task} A_{task}
- w_{distill} d_{OPD}
$$

where:

- $w_{task}$ corresponds to `task_adv_weight`.
- $w_{distill}$ corresponds to `distillation_loss_weight`.
- The final gradient is produced by the policy loss selected by `policy_loss_cfg`.

A minimal loss configuration is:

```python
from xtuner.v1.rl.loss import DistillationLossConfig

loss_cfg = DistillationLossConfig(
    policy_loss_cfg={
        "loss_type": "vanilla",
        "cliprange_low": 0.2,
        "cliprange_high": 0.28,
        "clip_ratio_c": 10.0,
        "log_prob_diff_min": -20.0,
        "log_prob_diff_max": 20.0,
    },
    loss_mode="k1",
    use_policy_gradient=True,
    task_adv_weight=0.0,
    distillation_loss_weight=1.0,
    use_kl_loss=False,
    mode="chunk",
    chunk_size=512,
)
```

This example is pure OPD: `task_adv_weight=0.0`, so training samples do not need task rewards. Set it to a positive value such as `1.0` to use task rewards as well.

## Teacher Top-K OPD

In Top-K OPD, the Teacher selects K tokens at every training position and provides both their token IDs and log probabilities. The Student computes its own log probabilities over the same token IDs, and XTuner then computes a differentiable distillation loss.

```text
Teacher forward
  -> Teacher Top-K token IDs + log probabilities
  -> Gather Student log probabilities at the same token IDs
  -> Top-K KL
  -> Direct backpropagation
```

The training-target contract is:

```text
target_token_ids: [B, T, K]
teacher_logprobs: [B, T, K]
```

Let $S_T$ be the Top-K set selected by the Teacher, and let $q_i$ and $p_i$ be the Teacher and Student probabilities for token $i$, respectively.

### `forward_kl_topk`

`forward_kl_topk` computes a truncated forward KL term only over the K tokens selected by the Teacher:

$$
L_{topk} = \sum_{i \in S_T} q_i(\log q_i - \log p_i)
$$

It does not combine probability mass outside the Top-K set into an extra tail bin. `log_prob_min_clamp` can bound Student and Teacher log probabilities from below before computation, while `loss_max_clamp` can bound the per-token loss.

### `forward`

In addition to the Teacher Top-K terms, `forward` combines the remaining probability mass into a tail bin:

$$
q_{tail}=1-\sum_{i\in S_T}q_i,\qquad
p_{tail}=1-\sum_{i\in S_T}p_i
$$

$$
L_{forward}
= \sum_{i\in S_T}q_i(\log q_i-\log p_i)
+q_{tail}(\log q_{tail}-\log p_{tail})
$$

### `reverse`

`reverse` weights the opposite direction with Student probabilities and also preserves the tail bin:

$$
L_{reverse}
= \sum_{i\in S_T}p_i(\log p_i-\log q_i)
+p_{tail}(\log p_{tail}-\log q_{tail})
$$

We recommend starting with `forward_kl_topk`, which matches the common Teacher Top-K training semantics:

```python
loss_cfg = DistillationLossConfig(
    policy_loss_cfg={
        "loss_type": "vanilla",
        "cliprange_low": 0.2,
        "cliprange_high": 0.28,
    },
    loss_mode="forward_kl_topk",
    use_policy_gradient=False,
    top_k=64,
    log_prob_min_clamp=-10.0,
    loss_max_clamp=10.0,
    task_adv_weight=0.0,
    distillation_loss_weight=1.0,
    use_kl_loss=False,
    mode="chunk",
    chunk_size=512,
)
```

Top-K modes do not place the distillation term in the advantage. Instead, they compute:

$$
L_{total}
= L_{PG}(w_{task}A_{task})
+w_{distill}L_{topk}
$$

Therefore, even when `use_policy_gradient=False`, `policy_loss_cfg` is still used for the optional task loss. The flag only means that the OPD term itself uses direct backpropagation.

## Configuring Teachers

### Let XTuner Launch the Rollout Teacher

Use `RolloutTeacherConfig.launch_config` to describe the Teacher service that XTuner should launch:

```python
from xtuner.v1.rl.distillation import (
    DistillationConfig,
    RolloutTeacherConfig,
    RolloutTeacherLaunchConfig,
)

distillation_config = DistillationConfig(
    loss_config=loss_cfg,
    teachers=[
        RolloutTeacherConfig(
            name="teacher",
            num_replicas=1,
            enable_prefix_caching=True,
            launch_config=RolloutTeacherLaunchConfig(
                model_path=teacher_model_path,
                num_workers=1,
                server_port=13141,
                dtype="bfloat16",
                tensor_parallel_size=1,
                expert_parallel_size=1,
                context_length=max_prompt_length + max_response_length,
                max_batch_size=2048,
                gpu_memory_utilization=0.8,
            ),
        )
    ],
    data_source_teacher_map={"math": "teacher"},
)
```

The OPD launch utility in this repository:

1. Reads `launch_config`.
2. Allocates GPUs and ports to each Teacher replica.
3. Reserves the remaining GPUs for Student workers.
4. Starts LMDeploy Teacher services and waits for their health checks.
5. Passes the actual endpoint map to the Trainer through `XTUNER_OPD_TEACHER_ENDPOINTS_JSON`.
6. Starts Student training and stops the Teacher processes launched by the utility when training exits.

Each Teacher replica must fit entirely on one node. The launcher allocates devices according to `num_workers` and rejects configurations in which Teachers occupy every GPU and leave no GPU for the Student. Keep `num_workers`, TP, EP, and the backend parallel topology consistent.

For an LMDeploy Rollout Teacher, set:

```bash
export XTUNER_USE_LMDEPLOY=1
```

LMDeploy Rollout Teachers support both sampled-token and Top-K targets.

### Connect to Existing Endpoints

If an external system manages the Teacher services, omit `launch_config` and provide `endpoints` directly:

```python
distillation_config = DistillationConfig(
    loss_config=loss_cfg,
    teachers=[
        RolloutTeacherConfig(
            name="teacher",
            num_replicas=2,
            endpoints=[
                "http://teacher-0:8000",
                "http://teacher-1:8000",
            ],
            api_key=None,
            request_timeout_s=1200.0,
            max_retry_per_sample=2,
            max_concurrency=128,
        )
    ],
    data_source_teacher_map={"math": "teacher"},
)
```

In this mode, XTuner does not start or stop the external services. It only performs health checks, request routing, concurrency limiting, retries, and response parsing. The number of `endpoints` should match `num_replicas`. Each endpoint must be the service root URL without `/generate`.

Multiple replicas of the same Teacher are routed deterministically using the Teacher name, data source, and rollout group. If a request to one replica fails, the client tries subsequent replicas according to `max_retry_per_sample`.

### Let the Training Engine Load the Teacher

Use `TrainTeacherConfig` for a Training-side Teacher:

```python
from pathlib import Path

from xtuner.v1.model import get_model_config_from_hf
from xtuner.v1.rl.distillation import DistillationConfig, TrainTeacherConfig

teacher_model_cfg = get_model_config_from_hf(Path(teacher_model_path))
teacher_model_cfg.compile_cfg = False

distillation_config = DistillationConfig(
    loss_config=loss_cfg,
    teachers=[
        TrainTeacherConfig(
            name="teacher",
            model_path=teacher_model_path,
            model_cfg=teacher_model_cfg,
            # When fsdp_cfg is omitted, XTuner creates a default
            # configuration with requires_grad=False.
            fsdp_cfg=None,
        )
    ],
    data_source_teacher_map={"math": "teacher"},
)
```

`model_cfg` must match the Teacher checkpoint, and it is recommended to use a configuration object separate from the Student configuration. The Teacher and Student may have different layer counts or hidden sizes, but they need compatible token-ID semantics. Current configuration validation requires them to have the same vocabulary size.

During Training Worker initialization, XTuner constructs the frozen Teacher and keeps it on CPU. Device transitions for each training phase follow this order:

```text
Actor and optimizer on GPU
  -> Offload actor and optimizer to CPU
  -> Onload Teacher to the training device
  -> Teacher computes targets
  -> Offload Teacher to CPU
  -> Restore actor and optimizer
  -> Compute old log probabilities and training loss
```

A Training-side Teacher does not create an HTTP service and does not need `XTUNER_OPD_TEACHER_ENDPOINTS_JSON`. CPU offload is currently supported; Teacher disk offload is not.

## MOPD and Data-Source Routing

`data_source_teacher_map` selects a Teacher using each training sample's `origin_data_source`:

```python
distillation_config = DistillationConfig(
    loss_config=loss_cfg,
    teachers=[
        RolloutTeacherConfig(name="math_teacher", ...),
        RolloutTeacherConfig(name="code_teacher", ...),
    ],
    data_source_teacher_map={
        "math": "math_teacher",
        "code": "code_teacher",
    },
)
```

Teacher names must be unique, and every Teacher referenced by the map must exist. Each data source participating in training should have a mapping; otherwise the Teacher-routing stage cannot generate the distillation targets required by that data.

### MOPD Behavior with Rollout Teachers

The rollout path completes routing before issuing an HTTP request:

```text
origin_data_source
  -> teacher_name
  -> matching RolloutTeacherClient
  -> Request only this Teacher
```

A sample does not request every Rollout Teacher.

### MOPD Behavior with Training-Side Teachers

The training engine first converts the `origin_data_source` of each sample into `teacher_indices`. The current implementation uses Teacher-major FSDP scheduling:

```text
for each Teacher:
  onload Teacher
  for each local pack:
    run the Teacher forward pass over the entire pack
    select tokens assigned to this Teacher using teacher_indices
    write only those positions into the final targets
  offload Teacher
```

Consequently, current Training-side MOPD runs every Teacher sequentially over every local pack and then selects results by token. It does not run only the routed Teacher for each sample. Both sampled-token and Top-K targets use this schedule.

This schedule ensures that every FSDP rank enters collectives in the same Teacher and pack order. Even if one rank has no tokens assigned to a particular Teacher, that rank cannot skip the Teacher forward pass independently, because ranks could otherwise enter different collective sequences.

The direct consequence is that Teacher forward computation grows as the number of Teachers increases. However, Teachers are onloaded and offloaded one at a time, so they do not reside on the training GPU simultaneously.

## Training-Objective Weights

OPD uses `task_adv_weight` and `distillation_loss_weight` to control the relative contributions of task reward and the distillation target.

### `task_adv_weight`

This value scales the advantage produced by task rewards:

- `0.0`: pure distillation; training does not depend on task rewards.
- `1.0`: use the full task advantage.
- Any other non-negative value: scale the task objective proportionally.

### `distillation_loss_weight`

This value scales the OPD target:

- sampled-token: scales the `k1` distillation signal added to the advantage.
- Top-K: scales the directly backpropagated Top-K distillation loss.

Common combinations are:

| Training objective | `task_adv_weight` | `distillation_loss_weight` |
| --- | ---: | ---: |
| Pure OPD | `0.0` | `1.0` |
| Equal task reward and OPD weights | `1.0` | `1.0` |
| Task reward as the primary objective, OPD as an auxiliary objective | `1.0` | `0.1` |

These values are not universally optimal. When tuning them, monitor reward, distillation metrics, policy ratio and clipping metrics, and overall training stability together.

## Launch Examples

The repository provides sampled-token OPD and MOPD recipes:

- `recipe/on_policy_distillation/config/rl_dapo_math_opd.py`
- `recipe/on_policy_distillation/config/rl_dapo_math_mopd.py`
- `recipe/on_policy_distillation/scripts/run_sampled_token_opd.sh`
- `recipe/on_policy_distillation/scripts/run_sampled_token_mopd.sh`

### Single-Teacher Sampled-Token OPD

```bash
export XTUNER_USE_LMDEPLOY=1
export WORK_DIR=work_dirs/dapo_math_opd

bash recipe/on_policy_distillation/scripts/run_sampled_token_opd.sh \
    /path/to/student \
    /path/to/teacher \
    /path/to/train.jsonl
```

### Multi-Teacher Sampled-Token MOPD

```bash
export XTUNER_USE_LMDEPLOY=1
export GSM8K_TEACHER_MODEL_PATH=/path/to/gsm8k_teacher
export GEO3K_TEACHER_MODEL_PATH=/path/to/geo3k_teacher
export WORK_DIR=work_dirs/dapo_math_mopd

bash recipe/on_policy_distillation/scripts/run_sampled_token_mopd.sh \
    /path/to/student \
    /path/to/dataset_meta.json
```

If the configuration uses external endpoints, the launcher does not create the corresponding Teacher processes. It still waits for endpoint health checks and passes the endpoint map to the Trainer.

A Training-side Teacher does not need `start_teacher_servers`. Add `TrainTeacherConfig` to a standard RL configuration and use the project's normal RL launch method; the Teacher is initialized together with the Training Worker.

## Metrics

Common sampled-token metrics include:

- `opd_reverse_kl`: mean `old_student_logprob - teacher_logprob` over valid tokens.
- `opd_abs_logprob_loss`: mean absolute log-probability difference.
- `reduced_distillation_kl` and `reduced_distillation_abs_loss`: unified distillation metrics.
- `teacher_score_time_s`: time spent by a Rollout Teacher scoring one state, stored in an extra field of the rollout state.

Common Top-K metrics include:

- `reduced_topk_opd_loss`: weighted Top-K distillation loss for the current batch.
- `reduced_topk_opd_kl`: mean Top-K KL over valid tokens.
- `reduced_topk_opd_student_selected_mass`: Student probability mass over the Teacher Top-K support.
- `reduced_topk_opd_teacher_selected_mass`: Teacher Top-K probability mass.
- `reduced_topk_opd_overlap_fraction`: mean overlap between the Student and Teacher Top-K sets.

Training-side Teachers also record:

- `time/train_teacher_compute`
- `time/train_teacher_onload`
- `time/train_teacher_offload`

Final distillation metrics are written under the `distillation/` prefix. Raw step averages from individual workers are also written under `train_metrics/worker_<rank>/`.

## Current Limitations

- Sampled-token supports only `k1 + Policy Gradient`.
- Rollout Top-K supports only LMDeploy.
- A single `DistillationConfig` cannot mix Rollout Teachers and Training-side Teachers.
- Training-side MOPD runs every Teacher sequentially over every local pack.
- Training-side Teachers support CPU offload but not disk offload.
- Current Top-K distillation uses Teacher-selected Top-K targets, not full-vocabulary distillation.
- A Reference Model and an OPD Teacher have different roles. Their configuration semantics remain different even if they use the same checkpoint.
